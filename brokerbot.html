Case Study 01 Real-estate AI · Multi-tenant SaaS

BrokerBot

Production agent infrastructure for real-estate workflows — the knowledge base, the agent, the harness, and the artifact engine on top.

Forward Deployed Engineer TypeScript · Python RAG · MCP · Evals brokerbot.ai →
01 · Problem

Agents that have to be right about messy enterprise knowledge.

BrokerBot is a real-estate AI platform. The hard problem was never "parse documents and embed them" — it was a real ingestion-and-agency platform problem: long-running workflow orchestration, fault tolerance, retries, cost control, structured extraction, and retrieval quality over heterogeneous, jargon-heavy, numeric real-estate data. Reliability and iteration speed were both required at the same time.

They needed someone to own that backbone end-to-end — the knowledge layer the agents reason over, the harness they act through, and the artifact pipeline that turns agent output into work clients can use. Not a feature contributor; an owner.

02 · What I built

The knowledge base, the harness, and the artifact engine.

  • Ingestion pipelineParsing, categorization, summarization, embeddings, and structured extraction across documents, web sources, and cloud-storage connectors — with durable orchestration, retries, and fault tolerance for long-running jobs.
  • Retrieval layerRetrieval quality tuned to real estate queries — long-tail, jargon-heavy, numeric. Citation-proven chunks so agent answers carry provenance a brokerage can defend.
  • Agent harnessA tool-calling loop over roughly 120 MCP tools with permissioned access to listings, documents, CRM, and email. Compliance-fenced prompts, human-in-the-loop gates where the workflow demands sign-off.
  • ObservabilityPer-step token and cost telemetry — every tool call attributable, every run replayable, unit economics visible as ingestion volume grows.
  • Artifact engineThe layer that lets agents ship finished work: verified PDFs, decks, flyers, websites, video, and audio — renders gated by automated verification, with failure → retry → pass behavior.
  • Eval gatesEval benches gate every release — prompt and tool changes don't ship without passing the suite.
03 · Engineering decisions

Where the leverage was.

  • In-house parsing over vendorReplaced a paid document-parsing vendor with an in-house stack that near-matches LlamaParse accuracy on the workloads that matter — the single largest cost lever in the system.
  • Verification as a gate, not a hopeArtifacts don't leave the pipeline unverified. A failed render retries against a spec; a render that can't pass never ships.
  • Telemetry per stepToken and cost attribution at the tool-call level, so a slow or expensive run points at a cause instead of a mystery.
  • Discipline at the language boundaryThe TypeScript ↔ Python seam is a known cost center — every cross-language hop is where errors silently degrade or latency stacks up, so it's treated as a designed interface, not an accident.
04 · What made it hard

The boring problems are the hard ones.

Real-world real-estate data resists tidy pipelines: partial scans, inconsistent metadata, long-tail jargon, numbers that have to be exact. Cost control on embeddings and LLM calls at production volume requires architectural discipline, not budget alerts. And retrieval quality has no single metric — it takes eval harnesses tuned to the actual queries the product sees in the wild, not a generic benchmark.

05 · Outcome

A platform the business runs on.

The knowledge base, agent, and harness ship production real-estate workflows today — and the artifact engine puts finished, verified deliverables in front of clients. The in-house parsing stack displaced a vendor contract while holding near-parity on accuracy.
